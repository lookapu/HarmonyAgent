# ArkTS 编译错误的 API 证据映射

`build_project` 在 ArkTS 编译失败后，会把结构化错误继续映射到当前工程 API 上下文、本机 SDK 类型定义和已入库的官方 API 变更记录。目标是让修复建议能回答“哪条定义不匹配、在哪个版本变化、当前产品是否可用”，而不是只返回泛化的“修复类型错误”。

## 证据链

每条类型、API Level、模块或符号解析错误按以下顺序处理：

1. 从编译器消息中的引号片段和 `@ohos.*` / `@kit.*` 模块名提取候选类型与 API 名；
2. 绑定本次构建选择的 product，解析 compile、compatible、target API Level 与本机 SDK API；
3. 在本机增量 SDK 索引中精确匹配模块和符号，并回读 `.d.ts` 声明行；
4. 在官方 API diff 数据库中查询同名 API 的 added、modified、deprecated 或 removed 记录；
5. 将证据附到原始源码位置，并把映射结果写入 `harmony.build.failed` Run 事件。

结果会区分三种映射：

- `type_constraint`：编译器明确报告赋值、参数、属性、重载或泛型约束不匹配；
- `official_definition`：本机 SDK 中找到与错误符号对应的官方声明；
- `api_change`：同时或单独找到官方版本变更记录。

## 安全边界

- 本机 `.d.ts` 是“当前能否编译”的最终类型依据，官方变更库用于解释版本历史；
- 只接受精确模块、API 名、类名或声明标识符命中，基础类型和模糊相似名称不会触发 API 迁移结论；
- 没有本机或官方证据时仍保留编译器的类型约束，但不会臆造替代 API；
- 诊断只提供证据和顺序化恢复步骤，不自动提升 `compatibleSdkVersion`，也不使用强制类型断言掩盖错误；
- 官方知识库为空或 SDK 未配置时自动降级，原始构建错误始终保留。

## 验收

单元测试覆盖“类型错误同时命中本机定义与官方引入版本”以及“仅有基础类型约束、没有 API 命中”两条路径。阶段门禁还需通过完整 Rust 测试、Worker 崩溃恢复、前端测试、lint、生产构建和 diff 检查。
