# 幂等写入的冲突键随数据形态漂移，UPSERT 退化成 INSERT

> 证据：`CHANGELOG.md` → `## Unreleased` → **数据**段。
> 「为什么没被立刻发现」一节为据现有材料重建，缺证据处标 `待补`，未补前不作为定论。

## 现象

同一批 API 知识库数据被反复刷新后，`api_docs` 表出现：

- `.d.ets` 伪模块名残留未清
- 同一个 API 的两代记录并存（旧的没被更新，新的一条被追加进去）

行数从应有的规模膨胀到远超预期，embeddings 与 `api_docs` 不再 1:1。

## 机制

刷新走的是 UPSERT（`INSERT ... ON CONFLICT DO UPDATE`），**依赖冲突键命中旧行**。
冲突键是按上一轮的数据形态定义的。

改用 HTML 正文解析后，抽取出的声明串与 Markdown 时代**不是同一个字符串** ——
HTML→Markdown 转换后的文本形态变了。于是同一份逻辑数据的**冲突键对不上**，
`ON CONFLICT` 永远不命中，语句静默降级为纯 `INSERT`。

结果：新数据全部追加、旧数据全部留存，同一 API 的新旧两代并存；
以 `.d.ets` 结尾的伪模块名因为键不匹配而从未被覆盖清掉。

## 复发模式

**任何影响 UPSERT 冲突键的数据形态变更——解析器、序列化格式、正则、归一化规则、
主键派生列——都必须与冲突键定义同一次提交。**

否则幂等写入会**无声地**退化成追加：不报错、不告警、退出码为 0，
只有行数对账和 1:1 断言能发现。

派生列尤其危险：`module` 这类从正文派生出来的键，换解析器后派生逻辑变了，
但列本身还在，于是老数据用新派生逻辑算出的键永远匹配不上老行。

## 钉住了什么

- UPSERT 补上 `module` 派生列刷新，并改为**空库重建**（不再叠加旧抓取代）——
  从"增量幂等"改成"确定性重建"，直接消除键漂移的累积
- 冲突键漂移本身无法靠单条断言发现；当前靠事后对账：
  伪模块名清零、embeddings 与 `api_docs` 1:1

## 对本项目的推广

`migrations/` 已有 84+ 张表。凡是"重跑即刷新"的写入路径（全量种子导入、
向量索引、评测基线、故障样本回流），都要问一句：

> **这次改动会不会改变参与冲突键的那一列的取值？**

会，就必须空库重建或显式清键，不能靠 UPSERT 兜。
`docs/FAILURE_REFLOW.md` 的回流流程第 2 步已经在做逐项 SHA-256 校验，
那是同一类问题在"重复导入"方向的防线。
