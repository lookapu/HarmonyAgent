第十八批起就记着「内部构成未普查」。第二十批先普查（只读），再拆。

打开设备面板会把分析面板和符号面板一起下载。**拆成 4 个模块后懒加载才真的生效。**

| | 拆前 | 拆后（打开该面板的下载量） |

| 符号检索 | 63.6KB | **13.0KB**（-80%） |

产物 chunk 数 137 → 140，index chunk 不变（这三块本来就是懒加载的，
省下的是**交互时的下载量**，不是首屏预算）。

- **位置**：`src/chat/components/devicePanels/{DevicesPanel,AnalyzePanel,SymbolsPanel,PerfCard}.tsx`
- **核**：`npx tsc --noEmit` + `npx eslint .` + `npx vitest run` + `npm run build`

#### 已普查：index chunk 里 65% 是框架，本仓代码里 64% 是 i18n 词库

方法：临时给 `vite.config.ts` 挂一个 `generateBundle` 钩子，导出
「chunk → 模块 → `renderedLength`」的表，构建后**按字节还原配置并核 sha256**
（不引新依赖，也不留痕迹）。`renderedLength` 是 **minify 前**的字节数，
**只能用来排序，不能当预算**；预算的真源永远是 `npm run build` 最后三行。

`index-*.js`（979.4KB minify 前 / 产物 564.4KB）：

| 项目 | minify 前 | 占比 | 可动吗 |
|---|---:|---:|---|
| react-dom | 458.7KB | 46.8% | 否 |
| **i18n 词库 en+zh** | **186.0KB** | **19.0%** | **见下** |
| 本仓其余源码 | 104.3KB | 10.7% | 部分 |
| react-router | 88.1KB | 9.0% | 否 |
| i18next | 73.7KB | 7.5% | 否 |
| 其他三方 | 52.1KB | 5.3% | 否 |
| react 本体 | 16.3KB | 1.7% | 否 |

框架合计 636.9KB = **65.0%，动不了**。本仓代码 290.4KB，其中 **i18n 两份词库占 64.1%**。

**唯一的真杠杆**：`src/i18n/index.ts` 静态 import 了 `zh.json` 与 `en.json`，
而**同一时刻只需要一种语言**。把非当前语言那份挪出首屏，按产物/minify 前

**这是产品决定，不是代码决定**：改成懒加载后，英文用户首屏要等一次动态
import（期间回落中文，会有可见闪烁），中文用户在切换语言时同样有窗口期。
**已登记为 P-4，等拍板。** 技术上怎么做（含避免闪烁的方案）留到决定之后再设计。

**纯算术**——为一次开方运算引入一个文件级 copyleft 依赖，代价与收益完全不成比例。

**契约 12 一上线就在真实官网上抓到一处真缺陷**：
`--site-accent-fg`(白) 压 `--site-accent`(#2f81f7) 只有 **3.75:1**；

所以拆出了 `--site-accent-solid`（承载白字的面）与 `--site-accent`（画在底上的字）。

**判据的已知边界**：算的是**设计稿上声明的色值**，不是浏览器算出的最终像素。
渐变、透明度叠加、图片上的文字都测不到——那需要 axe 或人工看。

### T-7 ~~i18n 死键清理~~ **（第十九批结清：删了 83 个）**

第十八批发现 `provider.current` 与 `home.switchModel` 搜字面量零命中，
但**故意没删**——删键需要「无任何动态拼接引用」的完整证据链。
第十九批先把证据工具建出来（`scripts/audit_i18n_refs.py`），再删。

**工具的四条判据**（缺一不可，理由见脚本 docstring）：

1. 完整点号**字面量**引用
2. **模板字面量前缀** —— 未枚举的族按**前缀保守覆盖**（宁可漏判不可错判）
3. **字符串/变量拼接** —— 必须登记在 `RESOLVED_DYNAMIC`，且与代码**双向对账**
4. **i18next 复数形式** —— `_one`/`_other` 单独保护（基键可以不存在）

**第 3 条是这个工具存在的核心理由**：多一个未登记的 `t(<裸变量>)` 就 **exit 2**。
一个不带条件的「死键列表」在有动态取键时是**危险的**——
它会把活键报成死的，而**把有效资源报成死的比漏报更误导**。

结果：**每个文件 2339 键 → 83 个可证死 → 删完 2256 键，死键候选 0**。
删完 `tsc` / `vitest` / 34 项验收全绿（没有一处在用它们）。

> 口径注记：审计头里的 **2341** 是 `en ∪ zh` 的**并集**键数，不是单文件键数——
> zh 侧存 `home.batchLines` / `home.batchQueue` 两个**基键**，en 侧走 i18next 复数、
> 存 `batchLines_one` / `batchLines_other`，并集恒比单文件多 2。
> 所以「2341 − 83 = 2256」是把两个口径相减，等式不成立（差值本身对）。
> 单文件口径 2339 − 83 = 2256，由删除脚本的 `set(after) == set(before) - set(dead)`
> 断言保证，是机器可核的。
> **别拿 `tsc` 绿来间接证明「没误删活键」**：审计同时输出
> `dangling`（代码引用但 i18n 无此键）= **0**，那才是正向证据。

**工具踩过的四个坑**（每个都写进 docstring 了）：

- Tailwind 类名里的 `0.5` / `1.5` 让「含点即 i18n 前缀」判据失效 → 248 个键被误判
- `a${Date.now()}` 的单字母前缀是 ID 前缀，不是 i18n 前缀
- 三元 `t(a ? 'x' : 'y')` 与插值对象里的拼接 `t('k', { n: a + b })` 被误判成动态出口
- i18next 复数键**永远不会被字面量引用**，不保护就会删掉 4 个还在用的键

- **重跑**：`python scripts/audit_i18n_refs.py --json <out>`

- 旧配置缺字段由 `AgentLimits` 的 `serde(default)` 补默认值，不会整份配置回退默认。

> 自测：`task_guard` 23/23（新增严格大于 / 护栏关闭不生效 / 只触发一次 / 进展后复位），

### T-11 语义索引 72.2% 是**逐字节相同**的向量（第二十三批登记 / **第二十四批根因被推翻**）

第二十三批普查向量库量出来的。**数据全部成立，根因判错了。**

| 项 | 值 |
|---|---:|
| 向量行数 | 44,856 |
| **唯一向量**（sha256 去重） | **18,506** |
| 属于重复组的行 | **32,381（72.2%）** |
| 重复组数 | 6,031 |
| **最大重复组** | **538 条完全相同的向量** |

**实测后果**（400 条随机查询，f32 暴力检索）：

| 指标 | 值 |
|---|---:|
| gap(top1 − top2) **恰好等于 0** 的查询占比 | **67.8%** |
| gap(top1 − top2) 中位数 | 0.000e+00 |
| gap(top1 − top5) 中位数 | 8.062e-03 |

**67.8% 的查询，其第 1 名和第 2 名在 float32 精度下完全并列。**

**为什么这个数很难靠「调参」绕过去**：给查询向量加 **σ=1e-3** 的噪声，
#1 结果变化 **0/150**——**并列不是「分数接近」，是「分数相等」**。

#### 被推翻的原始诊断（保留，因为 P-6 就是照它拍板的）

第二十三批的根因写的是：`doc_text` 只用 4 个字段，而 `version_label` /
`dts_file` / `api_level` 不参与，于是同一声明在几十个版本下拿到相同向量
（`version_label` 分布：5.0.0(12) **20,057 行**、26.0.0 5,708、6.0.0(20) 5,617…）。

**第二十四批推翻**：

| 项 | 原以为 | 实测 |
|---|---:|---:|
| distinct `doc_text` | 18,506 | **38,566**（文本去重只能省 6,290 行 / **14.0%**） |
| 剩余 20,060 个不同文本 | 版本并列 | **分词器把驼峰 API 名整段塌成 `[UNK]`** |

**决定性证据：`distinct token 序列 = 18,506` = `distinct 向量数 = 18,506`，一个不差。**
分词序列相同的行向量必然逐字节相同 ⇒ 碰撞 **100%** 由分词解释，版本不是原因。
（用 numpy+torch 写的参考实现把库里向量复现到 **1.1e-06**，并复现同样的碰撞 ⇒
权重、candle 推理、索引代码、DB 全部无责。）

**为什么上一批会判错**：`version_label` 不参与编码**确实是事实**，而 20,057 行
集中在同一个版本上看起来极像元凶——但**分母没打**。同一个"重复"现象有两个完全
不同的成因，而当时手上只有一个能同时解释两者的说法。**先分清「文本相同」
和「文本不同但向量相同」，前者是数据冗余，后者才是编码缺陷。**

- **重跑**：
  ① 文本去重口径 `SELECT COUNT(DISTINCT api_name||declaration||module||kit) FROM api_docs`
  ② 分词口径：全库分词后 distinct token 序列数，与 `COUNT(DISTINCT hex(vector))` 对齐
  ③ `[UNK]` 率：分词后 `[UNK]` token 数 ÷ 总 token 数（**现状 24.8%，修后 0.0%**）

### ~~T-12 `api_details.members` 与 `api_members` 9 行不一致~~ **（第二十四批结清：根因是那列**只写不读**）**

> **原诊断（保留，因为「先定哪边权威」这个问法把人带偏了半年）**：
> 两列「近乎重复但不同步」，**9 行不一致且都是 JSON 那边多**，
> 结论写成「这不是删冗余列能解决的：直接删 `members` 会让这些页面少 49 个成员」。

**那个推断的前提是错的。**页面显示的成员数**本来就来自 `api_members` 表**，
删掉 JSON 列**不会让任何页面少一个成员**——因为**没有任何读路径经过它**：

| 读的地方 | 实际读的源 |
|---|---|
| 知识库列表的「成员数」列 | `SELECT COUNT(*) FROM api_members` |
| 详情页的成员列表 | `FROM api_members WHERE detail_slug=?1` |
| Agent 检索命中的子项 | `FROM api_members` |
| 前端渲染 | 上面三条的后端返回 |
| 诊断包导出 | **根本不包含 `api_details` 这张表** |

手动新建详情那条路径更彻底：它给 `members` 写的是字面量 `'[]'`——
**连数据都没写过**。

⇒ **`api_members` 是唯一真源，`api_details.members` 是只写不读的冗余副本。**
那 9 行分歧是**症状不是病**：两个写入源口径不同（JSON 存抽取到的全部子项，
表里存 `INSERT OR IGNORE` 去重后的），而因为没人读它，分歧**永远不会冒泡**——
类型检查、lint、测试、构建、体积门禁全部绿灯。

#### 它有多贵（**又是净数据 vs 磁盘占用**，上一批刚被这个坑过一次）

| `SUM(LENGTH(members))` 净数据 | 15.2 MB |
| **实际磁盘占用**（复制 → DROP COLUMN → VACUUM → 比 `page_count`） | **21.9 MB** |
| 同一次 VACUUM 在「不删列」对照组上回收的 | 2.1 MB |
| ⇒ **净收益** | **19.7 MB** |

对种子库是 272.6MB 里的 **7.2%**；**剥离向量之后（93.7MB）占 21%**。

#### 真正卡住它的不是数据，是一句 `SELECT *`

`services/seed.rs` 原来是：

```sql
INSERT OR IGNORE INTO main.<t> SELECT * FROM seed.<t>
```

`SELECT *` 在 **seed 侧**展开列，插入却**按位置**写进 main ⇒ 要求两边**列数列序全同**。
老种子库还带 `members`、主库没有了 ⇒ 首次启动报
`table main.api_details has N columns but M values were supplied`，
而它在事务里 ⇒ **整批导入回滚** ⇒ **新装用户开箱即用的知识库直接空掉**。

**实测确认当时是「潜在的雷」而非已炸**：逐列比对 4 张表，主库迁移后与实际种子库
**列名列序全部一致**（`api_docs` 13/13、`api_details` 16/16、`api_members` 13/13、
`api_docs_meta` 2/2）。所以**删列必须与 `seed.rs` 那处改动同批上线**，
只上迁移不上改动 = 发行事故。

同一个坑**其实在这个文件里已经被撞过一次**：`api_docs_embeddings` 当年被单独
拿出来手工重映射，注释也写明了原因——但**修的是那一张表的症状，没动 `SELECT *`
这个成因**，所以它随时会从下一张表冒出来。

- **已落地**：迁移 `086_drop_api_details_members` + `seed.rs` 改成**运行时求交集**
  的显式列清单（`shared_columns`，不是写死列清单，那会随迁移一起过期）
  + `harmony_api_ref::store_detail` 与 `api_knowledge` 手动创建两处 INSERT 去掉该列。
- **重跑**：`PRAGMA table_info(api_details)` 应**没有** `members`。
  兼容性验证见 CHANGELOG 同批记录的端到端（**老种子库带该列也能正常导入**）。

### T-9 ~~失败调用的入参被丢弃~~ **（第二十二批更正：诊断错了，真相是「模型把占位符原样发了」）**

真正的问题在别处，而且更值得修：

三档各自的权益矩阵是否与现在一致。

### P-3 诊断包与「数据只落本地」承诺的关系

P2-1 承诺「数据只落本地不外发」（§6.15），而诊断包**必然含本地数据**。
脱敏边界已在 §6.23 落地（三道：模式脱敏 → 路径脱敏 → 用户内容地标），

### P-4 i18n 双词库要不要移出首屏（第二十批普查提出，**纯产品权衡**）

**已量化的收益**：`src/i18n/index.ts` 静态 import 了 `zh.json` 与 `en.json`，
两份词库合计 **186.0KB**（minify 前），占 index chunk 的 **19.0%**；
而**同一时刻只需要一种语言**。把非当前语言那份改成动态 import，
按产物/minify 前 0.576 的比例折算约省 **63KB**：
index chunk 564.4 → **~501KB**，余量 10.6KB → **~74KB**。

**为什么不是代码侧能直接决定的**：这换来的是一次可见的等待。
- 英文用户首屏要等一次动态 import，期间回落中文 → **会看到一次语言闪烁**
- 中文用户切换语言时同样有窗口期（除非额外做「先切、后取」的过渡态）

**需要先定的**：

1. 英文用户的首屏闪烁能不能接受？（本仓默认与 fallback 都是 `zh`，
   而 `readSavedLang()` 是**同步**读的 localStorage，所以英文用户**必然**命中这条路径）
2. 换语言时是否接受「先切到旧语言兜底、取到再切」的过渡？
3. 值不值：为 63KB 换来上面两个窗口期——而首屏预算还剩 10.6KB，
   **不做也不会立刻撞破门禁**。

**技术上怎么做到位（含避免闪烁的方案）留到决定之后再设计**，
不要在口径没定之前先写实现。

**决定（2026-10-01，第二十批）：暂不做。**

理由三条，都已量化：

1. **首屏还剩 10.6KB 余量**，不做也不会立刻撞破 `check-bundle-size.mjs`。
   「余量小」本身不构成现在就动的理由。
2. **换的是一次可见闪烁**。`readSavedLang()` 同步读 localStorage、
   而默认与 fallback 都是 `zh`，**英文用户必然命中**首屏等待这条路径——
   拿一个所有用户都看得见的观感问题，去换 63KB，不划算。
3. **收益是延迟兑现的**：这项优化真正值钱的时候是「余量反复被 i18n 键撑破」，
   而不是今天。

**重启条件（不要提前触发）**：index chunk 实测 **≥ 570KB**（即余量跌破 5KB）
**且**某一期的改动要靠新加 i18n 键才能过门禁。两条**同时**成立再启动。
在此之前，任何一批都不要再提「把词库挪出首屏」——它已经被量过、也被否过一次了。

> **为什么值得写死这条**：一个「已量过、已否过、附数字」的决定如果只活在对话里，
> 下一个批次会重新提一遍、重新量一遍、重新吵一遍。
> **把否掉的方案和它的数字留在台账里，比在「已否决」表里更管用**——
> 因为下次要做的是「重跑那个数」，而不是「相信一句结论」。

### P-5 工具标记的格式模板要不要改成「不可能被原样抄走」的写法（第二十二批）

系统提示在 5 处把格式写成 `【TOOL|工具名|JSON参数】`。实测有模型把 `JSON参数`
**原样当参数发了过来**（T-9）。识别器那侧已经能兜住并指名道姓地纠正，
所以这条**不急**，但模板本身确实是个可抄的坑。

候选写法与各自的代价：

| 写法 | 好处 | 代价 |
|---|---|---|
| `【TOOL|<工具名>|<JSON>】` | 尖括号一眼看出是占位 | 仍可能被原样抄，只是抄了之后报错更明显 |
| 给一个真实示例 `【TOOL\|read_file\|{"path":"src/main.ets"}】` | 抄了就是合法调用 | **模型可能照抄示例里的文件名去读**——从「调用失败」变成「读错文件」 |
| 保持现状 | 无 | 偶发占位符误发（现已能兜住并纠正） |

**这是产品/体验判断，不是技术债**：三选一都有代价，且取决于目标模型档位
（强模型自己会填占位符，弱模型更容易照抄）。**代码侧已把后果兜住**，
所以不必在口径没定之前先改措辞。

### P-6 语义检索要不要**版本感知**（第二十三批提出 → **第二十四批撤回重开**）

> **第二十四批结论：这条的前提被推翻了，原拍板（C：只要最新版 + 只索引自然键、
> 查询时 join 展开版本）已作废，不要按它实现。**

原问题是：44,856 条向量里 72.2% 逐字节重复，67.8% 的查询 top-1 与 top-2 完全并列，
所以「用户搜到一个 API，拿到的是哪一版」没有答案。用户据此拍板了 C。

**但 72.2% 那个数的分解是错的**（详见 T-11 的更正）：

| 层次 | 数量 | 性质 |
|---|---:|---|
| 文本本身就重复 | 6,290 行（**14.0%**） | 才是 C 能解决的那部分 |
| 文本不同但向量相同 | **20,060 个文本** | 分词器把驼峰 API 名整段塌成 `[UNK]`，**C 完全不解决** |

而 `distinct token 序列 = 18,506 = distinct 向量数` ⇒ 后者占 72.2% 中的绝大部分，
**与版本无关**。C 只能省 14.0%，却会把 28,131 行跨不同声明共享向量的问题原样留下。

**真正该先答的问题已经换了**（第二十四批已答一半）：语义检索在**中文查询 → 英文 API**
这个主场景上 top1 命中 **0/15**。修完分词后 top10 从 1/15 到 3/15——**必要不充分**。
剩下的差距是「中文句向量模型 + 100% 英文语料 + 4 层 small 档」这个**选型**问题。

**P-6 现在降级为一个小尾巴**：修完分词后仍同序列的只有 6,385 行（14.2%），且其中
大头是 `api_name` 为 NULL 的行（占全库 **29.1%**）——那是真重复，不是版本问题。

- **重开条件**：等分词修复合入、索引按新口径重建，且**向量层在端到端评测上打过 BM25**，
  再拿真实的「用户搜到 API 期望哪一版」问题来定。届时重复行数就是紧迫度。

### P-7 向量层是否值得留着（第二十四批新增）

> **第二十四批补充：先看这条实测，它改变了 P-7 的选项。**
> 用**生产代码本身**（`harmony_api_diff::search` + `relevance::Bm25Index`，
> 且 `cargo test` 默认不带 `embedding` feature ⇒ 向量块被 cfg 掉，量到的就是
> **生产纯关键词路径**）跑同一批检索词：

| 查询类型 | 关键词层召回 | 目标名次 | 向量层 top10 |
|---|---:|---:|---:|
| **语义 / 中文**（15 条） | **0 条（15/15）** | 未召回 | 3/15 |
| **精确标识符** `getWindowProperties` | 1 条 | **第 1 名** | — |
| `createWindow` | 6 条 | **第 1 名** | — |
| `getBundleInfo` | 8 条 | **第 1 名** | — |
| `WindowProperties` | 7 条 | 第 7 名 | — |
| `window` / `@ohos.window` | 50 条 | 第 26 / 25 名 | — |

**关键词层在精确标识符查询上 top1 3/3，是可靠且零成本的主力**；
在语义/中文查询上**一条都召不回**。原因是召回靠 `LIKE '%keyword%'` 字面子串，
而 `declaration` 含非 ASCII 的行 = **0 / 44,856** ⇒ 中文查询在关键词层无路可走。

**这条实测纠正了三个此前基于「BM25 是可靠底座」的错误推论**，包括
「关掉向量层、只留 BM25 + 前端版本筛选器」——那会让中文语义查询**彻底归零**。

第二十四批把「分词器缺陷」和「模型选型」拆开后，浮出一个更前置的问题：

| 项 | 值 |
|---|---:|
| 语料语言 | **100% ASCII**（`declaration` 含非 ASCII 的行 = **0 / 44,856**） |
| 语料内容 | 英文 TypeScript 签名，不是自然语言 |
| 模型 | `bge-small-zh-v1.5`（**中文**句向量模型，small 档 4 层） |
| 端到端（15 条真实检索词） | 现状 top1 **0/15**、top10 1/15；修分词后 top1 1/15、top10 3/15 |
| 代价 | 272.6MB 种子库（其中**向量表实测 178.9MB**，净数据 91.9MB）+ 91MB 模型随包分发 + 首次建索引 20~30 分钟 |

**语义层要重新证明自己比 BM25 关键词层有用**，否则它是在为一个不可用的能力付
存储、包体和首次运行时间。第二十四批已把「让向量层参与决胜」收窄为
**「有关键词命中时只在关键词集合内调序；关键词一条都没有时才放行」**
（见 `rrf_fuse` 文档），但**是否整体关掉**还没定。

四条路，都属产品判断，门禁不能替选：

| 方案 | 做什么 | 依据 | 裁决 |
|---|---|---|---|
| **① 保留并继续投入** | 换多语言/代码向量模型（需重新 vendoring + 过许可门禁） | 唯一能让中文语义查询真正可用的路；但要再买一次模型 + 重建全部向量 | **推迟**（见下方「已拍板」） |
| **② 默认关掉，保留为显式开关** | 精确标识符走关键词（top1 3/3，零成本）；需要语义时用户手动开 | 精确查询占 IDE 里的主要用法；关掉后省 **178.9MB** 种子库向量表（种子库 272.6 → 93.7MB）+ 91MB 安装包 + 首次 20~30 分钟 | **已落地**（§6.43） |
| **③ 彻底关掉** | 只留 BM25 + 前端版本筛选器 | **⚠️ 会让中文语义查询彻底归零**（关键词层实测召回 0/15）——已否决 | 否决 |
| **④ 降级为「索引体积优化」用途** | 省掉并行的全表向量表 | 与②重叠，见取舍 | 与②冲突（任何中断都会留下半成品表） |

> 同 P-6：**不能靠门禁硬指定**。门禁可以要求写出理由。
> ④ 那条在第二批十三批就已存在，本批不重复裁决。

### 已拍板（2026-10-08）：**按 ② 发版，① 推迟**

**决定**：本轮发行**按方案②**（语义检索默认关、显式开关），**不投入①**。

4. 种子库剥离后省 **178.9MB**（272.6 → 93.7MB），这是②的实收益，

### ① 的重启条件（**可判定**，不是「以后再说」）

先说一个被否掉的候选条件：**「上线后看用户实际用得少」**——
**它不可判定**：`usage_events_enabled` **默认关闭**（键不存在即关闭），
且 `EVENT_NAMES` 白名单里**没有任何检索相关事件**。
⇒ 默认状态下**没有数据可看**，拿它当条件等于永远不重启。

所以重启条件只写**代码侧可测的事实**，三条**同时**成立：

| # | 条件 | 怎么判 |

| 1 | 出现**能被向量层救回**的真实查询（关键词层 0 命中、且语义层 top10 有目标） | 按 `dv-e2e` 口径跑真实检索词 |
| 2 | 该类查询**成规模**（不是个案）：≥15 条真实检索词中 ≥3 条属于此类 | 同上一条口径统计 |
| 3 | 已有**许可合规**的多语言/代码向量模型可 vendoring（BSD-3 / MIT / Apache-2） | 过 `scripts/check-licenses.py` |

**缺一不可**：①1 而无② = 个案，不值一次模型采购 + 全量重建；

> 上一批我们否决 P-4 时写的是「index chunk ≥ 570KB 且某期要靠新 i18n 键」——

> 下个批次会重新提一遍①、重新吵一遍。

- **重跑**：见 T-11 重跑 ②③；端到端命中率按 `dv-e2e` 口径（15 条检索词，目标 API
  须先核实存在）重算。
  **关键词层基线（务必一起量，否则又会得出「向量层没用」的错结论）**：

**第二十批补上的第 4 道（第 15 道门禁，`check-lazy-graph.py`）**：

4. **「懒加载是否真的生效」——已补门禁。**
   §6.35.1 那个缺陷是**静默**的：三行 `lazy()` 全都指向同一个模块，
   `tsc` / `eslint` / `vitest` / `build` / 体积门禁**全绿**——
   因为「同一个模块」在类型和语义上都没错，只是**没有分包**。
   `check-lazy-graph.py` 拦的是**客观为空操作**的两种：
   ① 目标路径拼不出文件（面板会永远不出现，现有门禁无一报红）
   ② 目标已被静态 `import` 触达（它已经在首屏包里，`lazy()` 什么也没省）
   - **真源现状**：24 处 `lazy(() => import('X'))`（`App.tsx` 19 个页面 + `Home.tsx` 5 块面板），
     另有 2 处 `lazy(` 只出现在注释里，判据已能区分。
   - **自测 10 条，负向验证 15/15**（真源注入两条缺陷各红一次，还原后按字节回到原 sha256）。
   - **本门刻意不判**：「N 行 lazy 应当是 N 个不同模块」。
     多个组件共用一个懒加载模块是**合法**写法，硬指定会逼人把合法的也改掉——
     那是「硬指定统一答案」，不是门禁。要表达「这几块必须各自成块」靠的是模块边界。
   - **仍未覆盖**：把三块面板合回一个文件，在语义上完全正确，本门判不出来。
     那是**意图与事实的偏差**，只有代码评审能拦。

**第三十一批补上的第 5 道（第 21 道门禁，`check-tauri-events.mjs`）**：

5. **「事件名对不对得上」——已补门禁，但只管到事件名这一层。**
   - 判据只比**名字**：`listen('x')` 的 `x` 与后端 `emit` 的 `x` 是否同一个。
     ~~**payload 结构不判**~~ —— **第三十三批起补上了载荷字段对账**
     （见下面「第三十三批给第 21 道门禁补上的一段」）：
     前端 `listen<{ a: string }>('x')` 声明的字段必须存在于后端
     `emit("x", OtherStruct { … })` 的序列化结果里。
   - **载荷对账的已知边界**：
     - 只在**两侧都解得出**时比对（前端须是内联对象类型、后端须是结构体字面量），
       `json!` 载荷与命名类型比不了 ⇒ 每次跳过都留 note；
     - 判据方向只有「**前端 ⊆ 后端**」一个方向（后端多发字段不是缺陷）；
     - 比对组数带**下限守卫**（当前 24 组），抽取规则失效会报红而不是静默通过。
   - 也不判**同名的两套语义**：`chat-done` 这个名字在两端都存在，
     但若后端某天把 payload 字段改名了，~~本门照样绿~~ ——
     **第三十三批起会判红**（前端仍声明旧字段名时）。
   - Rust 侧按**字面文本**解析。若将来改用宏批量生成 `emit` 调用，
     判据 1/2 会**全部落空**——所以判据 3 必须守住「发射集合为空就报红」。
   - **枚举不完整时自动降级**：只要还有一个发射点的事件名定不出来，
     「没人发 X」就只是上界而非事实 ⇒ 本门降级为**只报告**并写明原因。
     这与 IPC 门禁的方向**相反**（那边的动态是调用点，落在「没人调」那一侧）。

**第三十三批给第 21 道门禁补上的一段：载荷字段对账**

事件名是字符串字面量，**载荷字段名同样是字符串**——
前端 `listen<{ conversation_id: string }>` 手写，
后端 `pub struct XxxEvent { … }` 也手写，**两侧编译器互不相识**。
⇒ 字段名拼错时：类型检查绿、单测绿、构建绿、运行时不报错，
那个字段**恒为 undefined** ⇒ 功能静默失效。
而本门此前只管**事件名**，对字段名**完全无感**。

| 项 | 口径 |
|---|---|
| 前端侧 | `listen<{…}>` 的**内联对象类型**（命名类型需跨文件解析类型定义，本门不做） |
| 后端侧 | **结构体字面量**载荷（`json!` 与表达式载荷本门不做） |
| 判据方向 | **前端 ⊆ 后端**（后端多发字段不是缺陷，查了会误报） |
| 当前覆盖 | **24 组**前后端载荷字段，全部一致 |

跳过的情形**都留 note**（不能静默跳过），且带**比对组数下限**守卫——
抽取规则一旦失效会直接报红，而不是静默变成「无问题可查」。

**写这段时当场踩到两个真 bug（都不是「漏判」，是「算错」⇒ 表现为误报）**：

1. **私有字段也是要序列化的。** 解析器第一版只认 `pub` 字段，
   于是 `GenDoneEvent` 等 4 个结构体（字段**全是私有的**）被解析成「零字段」
   ⇒ 门禁误报 4 处「前端声明的字段后端不存在」。
   ⇒ serde 的派生实现与结构体**同模块**，私有字段照样会被序列化。
   （假阳性不是「无害的误报」——**它会让人去改本来正确的后端代码**。）
2. **`String.replace` 的 replacer 没有 `.index`。**
   `replace` 的回调签名是 `(match, ...captures, offset, string)`，
   `.index` 是 `RegExp.exec` 才有的。
   写成 `m.index` 得到 `undefined` ⇒ 属性位置算成 `NaN` ⇒
   「这个 serde 属性属于哪个字段」的比较恒为假 ⇒ `skip` / `rename` 串到上一个字段上。

## 六、已修复的偶发失败（**记录成因，避免重犯**）

### `services::seed` 测试偶发 3/4 失败 —— `%TEMP%` 残留 + 目录名带 pid

**现象**：全量 `cargo test` 跑出 3/4 失败，**单独跑同一批 4/4 通过**，
重跑全量又 1211 条全绿。报的是 `table api_docs already exists`。

**成因**：四个测试的临时目录是
`%TEMP%\deveco-seed-<tag>-<std::process::id()>`，而 `seed.db` 是在
`Connection::open(&seed)` 上建表的——**`create_dir_all` 对已存在的目录是成功的，
不报错**。所以「上一轮被中断（Ctrl-C / CI 超时 / 机器重启）留下的 `seed.db`」
不会让文件系统层失败，而是让 SQLite 层在 `CREATE TABLE` 时炸。
原代码只在**结尾**清理，进程一被中断，清理那行就永远执行不到；
而 pid 会被系统复用，于是新进程算出同一个路径。

**修法**：四个测试都在建目录**之前**先 `let _ = std::fs::remove_dir_all(&dir);`
（结尾那行保留）。共 8 处调用。

**负向验证 19/19**，含真对照：

| 组 | 预置残留 | 期望 | 实得 |
|---|---|---|---|
| 对照（摘掉修法后重编译） | 有 | **必须失败** | 失败，且报 `table api_docs already exists` |
| 实验（还原后重编译） | 有 | **必须通过** | 连续 3 次 4/4 通过，输出无 `already exists` |

**验证里两个真踩到的坑**（都写进了脚本 docstring）：

- 目录名带 pid，而「知道 pid」与「预置残留」在时间上**互斥**。用 Windows 的
  `CREATE_SUSPENDED` 把新进程冻在第一条指令之前，`Popen` 立刻返回 pid，
  此刻预置残留，再用 `NtResumeProcess` 放行。
- 第一版把摘除锚点写成**跨行字符串**（`"…3/4 失败。\n        let _ = …"`），
  而该文件是 CRLF，`。\r\n` 里那个 `\r` 让它**匹配 0 处**——
  `str.replace` 匹配 0 处时安静地返回原串，于是「摘除没发生」和「摘除成功」
  长得一模一样，对照组于是拿**没被破坏的代码**去要求它失败。
  改成**按行手术**，并当场断言「8 次变 7 次」。

**泛化**：任何在 `%TEMP%` / 工作区建目录的测试，清理都必须**开头也做一次**；
只写在结尾的清理，在「进程非正常退出」这个**唯一真正需要它**的场景里恰好不会执行。

### 质量分在**零判据**时报 100 分 —— `all()` 作用在空集合上（第二十一批已修）

**现象**：一句「现在项目什么情况？」跑出
`quality_json = {"score":100,"acceptance_passed":true,"evidence_criteria":0}`
且 `acceptance_json = {"criteria":[],"evidence_count":0,"passed":true}`。
21 次成功工具调用**全部**是 `verification_state=none` +
`contribution_state=no_direct_acceptance_evidence`。

**成因链**（四层，每层单独看都「正确」）：

1. `agent/acceptance.rs:55` —— 目标不含变更/构建/测试/部署/提交/推送任一关键词
   ⇒ `GoalContract::compile` 生成 **0 条判据**（纯问答的正常形态）
2. `agent/acceptance.rs:321` —— `passed: blockers.is_empty()`
   作用在**空集合**上，恒为 `true`
3. `agent/governance.rs` —— 打分从 100 起，只按 `passed`/`exhausted`/
   `remediation_count` 减，**没有「判据为空」这一项** ⇒ `score = 100`
4. `commands/reliability.rs` —— 无条件累加进 `average_quality_score`，
   `CostPage.tsx` 的 `scoreTone(>=90)` 把它显示成**绿色**

**最深的一层**：`false_completion_count`（唯一专门抓假绿的指标）判的是
`state == "completed" && passed == Some(false)`——**未受裁决的运行 `passed` 是
`Some(true)`，结构上永远进不了这个计数器**。抓假绿的探测器看不见空判据，
因为在它眼里空判据和真通过**没有任何区别**。

**修法**（不是把 `passed` 改成 false——那会让**所有纯问答永远无法完成**，
而 `GoalContract::directive` 对空判据本就退化成「纯问答：给出准确完整结论」，
说明这是**契约的固有形态**而不是缺陷）：

- `RunQualitySnapshot` 加 `criteria_declared` / `unscored`，
  `schema_version` 1 → 2；未受裁决时 `score` 恒为
  `UNSCORED_QUALITY_SCORE`(0)。**取 0 不是折算，是让忘记看标志位的下游
  显示为「不可信」而不是「完美」——错向安全那一侧**
- **没有伪造判据**：给纯问答硬造一条「答案引用了工具证据」，
  那是造一个恒真的式子，正是本项目反复踩的坑
- `reliability.rs`：未受裁决的运行**排除在均值之外**（不折算成 0 拉低整体，
  否则「质量分」会同时被两种错误污染），并新增 `scored_runs` / `unscored_runs`
- `CostPage.tsx`：`scored_runs === 0` 显示 `—`。**这里不能显示 0.0**——
  「没有一轮被裁决过」会被读成「质量极差」，与事实相反
- 历史行没有 `unscored` 键，按**受裁决**处理，不追溯改写历史统计

**自测 2 条**（`governance.rs`）：
① 反例直接用真实那句「现在项目什么情况？」，断言 `unscored` 且 `score != 100`，
且 `remediation/recovered/exhausted` 全拉满也不许涨分；
② 判据非空时打分**原样保留**（全通过 100 / 无证据 55）——
拿纯问答修真实回归是这一类改动最常见的失败方式。

### `todo_write` 静默丢弃状态变更 —— 被文档化的用法恰好是失效的用法（第二十一批已修）

**现象**：模型把 5 项全标 `done`，工具回
`任务清单未变化：共 9 项，已完成 0，进行中 0，待处理 9（内容与上次完全相同）`。
三方自相矛盾：它说要变、工具说没变、**工具自己的账说还是 9 项全待处理**。

**成因**：`agent::todo::render_hint` 每轮注入系统提示，明确教模型
「完成一项就立刻用 `todo_write`（**merge=true 只传变化项**）把状态改成 done」
——也就是只带 `{id, status}`、**不带 `content`**。而 `tools/mod.rs` 的解析器
对空 content 一律 `continue`：**整条状态变更被静默丢弃**，
随后 `unchanged` 判成 true，于是回「内容与上次完全相同」。
模型看不见丢弃、只看见「未变化」，于是继续以为清单已更新。

**修法**：解析逻辑抽成纯函数 `parse_todo_items(arr, merge, before)`，
merge 模式下按 id 从现清单**继承 content**；继承不到（确实是新项）才丢弃，
并把丢弃项的标识**回报给模型**——静默丢弃正是本缺陷的成因，不能悄悄地不处理。
`replace` 模式（`merge=false`）没有现清单可继承，维持原样丢弃。

**自测 4 条**，第一条**原样复现真实入参**（5 项只有 id+status）；
另外三条分别钉住反向（未知 id 必须被点名）、`replace` 模式不被顺手改宽、
既有行为（缺省 id 补 `t{n}`、缺省 status `pending`）不变。

**负向验证时踩到的第三个同形坑（重要）**：

第一版脚本的「尾」判据报「还原后仍红」，而 sha256 证明文件**逐字节已还原**。
根因：`shutil.copy2` **保留 mtime**，还原后源文件 mtime 比「注入版那次构建」
还旧，**cargo 按 mtime 判新鲜度就跳过重建**，跑的还是注入版二进制。

> 「注入无效」和「判据没生效」在退出码上完全一样，这次是**第三种**：
> **「还原了但没重新编译」**。文件正确、二进制错误、判据照样红。
> 修法：还原后 `os.utime(path, None)` 顶到当前时间强制重编。
> 凡是**用编译型判据做负向验证**，还原后都必须显式 bump mtime——
> 字节级还原干净**不等于**行为级还原干净。

### `check-self-test-counts.py` 在**中文 Windows 上一直是红的**（第二十四批末已修）

```python

return r.returncode, (r.stdout + r.stderr).decode("utf-8", "replace")
```

子门禁的 stdout 是**管道**，Python 按 locale 写——中文 Windows 是 **GBK**；
父进程却按 **UTF-8** 解码 ⇒ 乱码 ⇒ `parse_count` 读不出数字
⇒ **6 道门同时报「读不出用例条数」**。真实 A/B：

| 环境 | 退出码 |
|---|---:|
| 不设 `PYTHONIOENCODING` | **1**（假红，6 项） |
| 设 `PYTHONIOENCODING=utf-8` | **0** |

**为什么一直没人发现**：CI 是 Linux/UTF-8，永远绿；而本地开发者跑它时，
大多经 `scripts/deveco-verify-all.py`——**那个验收器给子进程注入了变量**，
注释里写的就是「免得再出现一个符号的编码问题伪装成一道门坏了」。
**同一个补丁打在了验收器上，没打在门上。**

修法是给 spawn 加 `env={**os.environ, "PYTHONIOENCODING": "utf-8"}`。
变异验证：删掉这一行 ⇒ 本机立刻回到退出码 1；还原后 sha256 一致。

> **泛化**：**修「症状出现的地方」不够，要问「谁让它出现」**。
> 这里的症状在解析结果里，成因在 spawn 时没带环境。
> 另一条：**一个只在某台机器上复现的缺陷，最可能的成因就在那台机器的环境里**，
> 别急着在逻辑里找。CI 绿 ≠ 没问题，只等于「在 CI 那种机器上没问题」。

#### 反向审查时才发现的一个真漏洞：**白名单会从豁免变成漏洞**

第一版只判「未登记的重复键要拦」。假设某天有人修好了 `zh.json` 的 `home.timeline`
却忘了删白名单条目，那么**同一个键将来再写一次重复，会被静默放行**——
白名单就从豁免变成了漏洞，而且**没有任何一处会报红**。

⇒ 白名单必须与真源**双向**对齐：**未登记的要拦，已失效的也要拦**。
这条在白名单非空时还顺带给了判据本身**第二道网**：M1 / M3 把判据弱化之后，
真源从绿变红——**红的原因不是「重复键没查出来」，而是「登记的 5 处已经找不到了」**。
判据被改坏时白名单自己会喊，这个交叉验证是意外收获。

> **泛化**：任何白名单/豁免表都要问一句「**条目失效时谁来说话**」。
> 只做单向（挡住未登记的）的那一半，是**最容易被当成已经做完**的一半。

#### 自测当场抓到我自己写错的一个 bug

### 手写词法分析器 = 自己造了一个更差的 TypeScript 编译器（第二十七批实测）

- **实例**：第 18 道门禁第一版用 Python 手写状态机剥注释，再匹配 `t('x.y')`。
  注入一个坏键跑它，**门禁是绿的**。追下去发现它把真引用吞光了：

  `Markdown.tsx` **27 个全丢**。

  `` `${...} `` 里面是**真代码**，而状态机把整段模板当字符串置空了。

- **判据一**：**仓库里已经有 TypeScript（`tsc` 天天跑），该用它而不是自己造一个。**
  改用 `ts.createSourceFile` + AST 遍历后：引用一个不丢、注释里的死键照常不算、
  注入坏键立刻报出精确的 `file:line`。自测里专门加了一条
  **「模板插值里的要算」**——它就是第一版实丢 380/424 的那类。
- **判据二**：**「门禁是绿的」在注入测试里是一个结果，不是一个结论。**
  第一轮变异 N1 / N2「无人承重」几乎把我推向「判据是装饰」的结论，
  真因是**判据本身根本没在工作**（真引用被吞 ⇒ 注入的坏引用也一起被吞）。
  「没人守」有两种：守卫没建，和守卫建了但一直是死的——**先分清是哪一种**。
- **配套**：门禁语言不必统一。本仓已有 Node 门禁（`check-bundle-size.mjs`），
  于是 `check-self-test-counts.py` 与验收脚本的清单正则都扩到 `py|mjs`。
  ⚠️ 只认 `.py` 时它报的是「台账缺 N 道门」——
  **看起来像文档问题，实际是解析口径问题**，容易往错的方向修。
- **泛化**：任何要「读懂代码」的检查（注释剥离、死代码、命名规范、import 图、调用图）——

### 刚交付的门禁自己有三个假阴性，是被一次**死键普查**撞出来的（第二十八批）

### 新门禁**第一次跑就报出了假全绿**（第三十批）

修的时候还差点修反方向：自测里我写了

动态调用只让「**没发现缺失**」这个结论变成上界，
它**不压制**静态已经看见的**真缺失**：
`invokeWithError('no_such_cmd')` 是一个字面量，它确实没注册，必须照报。

### 「零生产调用者」是线索，不是结论（第三十批）

探针报出 9 个 IPC 命令前端不调用。我顺着查底层函数，
发现 `scheduler::claim_next` **零生产调用者**，于是推断：

**读代码之后这个推断被推翻**：`scheduler::register_active`
（生产路径，由 `commands/chat.rs:4849` 调用）在 `enqueue` 之后
**就地**用一条带并发键保护的 `UPDATE ... WHERE state IN ('queued','recovery_required')`

而 `claim_next` 是给**外部 worker 轮询**用的拉取式 API——
桌面端是单 worker，本来就没有轮询方。

> **泛化**：调用图分析、死代码检测、覆盖率报告、未使用告警。
> ⚠️ 注意本项目已经踩过两次「grep 出来的『没用上』是假的」：
> 一次是 i18n 键藏在三元表达式里，一次是本节的 `claim_next`。


### 「事件名解析不出来」和「事件名解析错了」是两种失败，后者更贵（第三十一批）

第 21 道门禁（`check-tauri-events.mjs`）管「前端 listen 的事件名必须在后端 emit」。
它与第 20 道门禁同构：事件名是字符串字面量，后端改名/删事件**前端不会编译报错**，
运行时也不报错——`listen` 一个永远不来的事件只是**永远不触发**，
症状是「某个功能就是不动」，且**没有任何地方报错**。

探针第一次报「前端监听但后端不 emit：**4** 个」。逐个查证后：

| 事件 | 真相 |
|---|---|
| `node-runtime-progress` | 后端**有发**，但事件名藏在 `const EVENT: &str = "…"` 后面 |
| `git-runtime-progress` | 同上 |
| `jdk-install-progress` | 同上，且藏在**另一个文件**的常量里 |
| `chat-reasoning` | 后端**从来没发过**——真的死监听 |

⇒ 前三个是**假阳性**，第四个才是真的。

> **判据一**：**解析不出来**和**解析错了**是两种失败，代价不对等。
> 解析不出来 ⇒ 保守（少报，或降级为只报告）；
> 解析错了 ⇒ **假阳性**，而**假阳性比假阴性更贵**——
> 它会让人去删一个活着的监听，把一个能跑的功能改坏。
> ⇒ 宁可漏报，不可误报。**「我没看见」和「它不存在」不是一回事。**
> **泛化**：任何跨语言/跨层的名字对账（RPC 名、事件名、路由名、主题名、图标名）。

事件名的解析分三层，**缺一层就产生假阳性**：

1. **字面量**：`.emit("chat-stream", …)`
2. **同文件常量**：`const EVENT: &str = "node-runtime-progress"` + `.emit(EVENT, …)`
3. **跨文件辅助函数参数**（含**透传**）：

```rust
// services/runtime_progress.rs —— 事件名是函数参数
pub fn emit(app: &tauri::AppHandle, event: &str, p: &RuntimeProgress) {
    let _ = app.emit(event, p);
}
// services/node_runtime.rs —— 事件名是调用方的常量
const EVENT: &str = "node-runtime-progress";
runtime_progress::emit(app, EVENT, &RuntimeProgress::phase("check", "…"));
```

第 3 层里还有一层透传：`runtime_progress::download_to_file(app, EVENT, …)`
的体内把同一个参数交给同文件的 `emit(app, event, …)`。
⇒ 「事件源」用**不动点**求出：函数把自己的参数传进另一个事件源的事件槽时，
它自己也是事件源。

裸字面量正则只能看到 **90/91** 个 `.emit(` 调用点。

### 「动态」在不同方向上的极性是**相反**的（第三十一批）

第二十七批的「上界不许吞掉事实」在本批要**分方向**用：

- **IPC 门禁**里动态的是**调用点**（`invoke(cmd)` 的 `cmd` 是变量）
  ⇒ 它让「没人调它」变成上界，**不压制**静态看见的真缺失 ⇒ **仍然判红**。
- **事件门禁**里动态的是**发射点**（`app.emit(name, …)` 的 `name` 定不出来）
  ⇒ 它让「没人发它」变成上界 ⇒ 「这是死监听」**不是事实** ⇒ **降级为只报告**。

⚠️ 写成同一个模板就会判反方向：事件门禁若照抄 IPC 门禁「动态也判红」，
就会把一个**可能活着**的事件报成死的。
⇒ **判据有上界时，先问「上界落在哪个方向」，再决定降不降级。**

### 「一处做分类」与「只给一侧写守卫」是同一个坑的两种形态（第三十一批）

变异 N6 往真源里塞了一个 `app.emit(__mut_dyn, ())`（局部变量），期望门禁**降级为只报告**。
实测门禁**照常按完整集合判红**——因为那个点被**静默丢弃**了。

真因：分类逻辑被拆在两处——`scan()` 处理字面量与常量，
`resolveSourceNames()` 处理事件源，而「标识符既不是常量也不是事件源参数」这一路
**两边都没管**。

> **判据二**：**分类必须一处做完。** 「哪些是事实、哪些是不可判定的」是**同一个问题**，
> 拆到两个函数里就必然漏掉交叉的那一类。
> 这与第三十批「只给一侧写零条守卫」是同一个坑的两种形态：
> 那次是**解析步骤**漏写一次，这次是**分类维度**漏写一格。
> **泛化**：任何「把输入分成若干类，各走各的判定」的流程——
> 类型分派、错误分类、协议版本分流、差分同步。
> ⚠️ **症状都是一样的：漏掉的那一类被静默丢弃，而门禁照常显示「通过」。**

修法：抽出一个 `classifyEmitSites()` 统一分类，返回「已定值」与「不可判定」两桶；
自测里补两条——定不出的点必须进不可判定桶、事件源覆盖的点不得误进。

### 真实发现：`chat-reasoning` 是一条从来没人发的死订阅

后端把正文与思考增量**合并**进 `chat-stream-batch` 事件
（`StreamEventBatcher` 的 `flush()`），**不再单独 emit `chat-reasoning`**；
而 `chat.rs` 里那条 `/// 思考增量（透传 emit chat-reasoning）` 的注释还在按旧设计描述。

⇒ 桌面端 `chatSlice.ts` 挂着一个**永远不会触发**的 `listen('chat-reasoning', …)`；
LAN 桥白名单 `EVENT_WHITELIST` 里也躺着同一个死条目；LAN 网页端还有一个
`on('chat-reasoning', () => { /* keep alive */ })` 的空监听。

三处一并清掉（桌面监听 / 白名单 / 网页端空监听），并改掉那条陈旧注释。

> **判据三**：**同一类问题的三个副本会一起腐化。**
> 一个事件名同时出现在「后端发射」「桌面端订阅」「LAN 转发白名单」三处时，
> 任何一处的改动都不会自动带动另外两处——它们只是**看起来**像在互相约束。
> ⇒ 跨副本的一致性要么用**单一真源**（常量导出），
> 要么用**对账门禁**把三处放在一起比。
> **泛化**：配置副本、协议副本、清单副本、文档副本。

### 差点把「有人守」写成「没人守」——粗网与细网是两层，不是一层（第三十一批）

写完门禁跑全量门禁时，`cargo test` 报了一个**我没预期的**失败：

```
test every_frontend_event_exists_in_backend ... FAILED
前端订阅了 Rust 侧不存在的字面量事件名（多半是拼写不一致）：["chat-reasoning"]
```

`src-tauri/tests/frontend_backend_contract.rs` 里**早就有**一个事件对账测试。
也就是说这一面**并不是没人守**——我选题时没先搜一遍，
差点把第二十九批那条教训（「写『现状缺口』之前，先去搜它是不是已经被守」）
又犯一次。

两者的分工必须写清楚：

| | `frontend_backend_contract.rs`（粗网） | `check-tauri-events.mjs`（细网） |
|---|---|---|
| 前端抽取 | **正则**（会吃到注释与跨段文本） | **TypeScript 解析器** |
| 后端判定 | 字面量 `"X"` **在 Rust 源码里出现过**（注释、白名单、常量都算） | 后端**真的 emit** 它 |
| LAN 白名单 | 不看 | 判**死转发** |
| 判红方向 | 缺字面量 | 死监听 / 死转发 |

⇒ 粗网漏掉的（**字面量被提到但没人发**）正是细网抓的：
`chat-reasoning` 当时在 LAN 白名单与文档里都有字面量，粗网**放行**，
细网判红。**两层都要留着。**

> **判据四**：**粗网与细网不是同一层的两种实现，是两层。**
> 把「已经有粗网」当成「已经有守卫」而跳过细网，粗网的漏报就会一直漏下去；
> 把「已经有细网」当成「可以删掉粗网」，则会因为运行环境不同（脚本要 Node、
> 契约测试只要 cargo）丢掉一层。
> **泛化**：任何分层防御——限流 + 熔断、类型检查 + 运行时校验、
> 静态扫描 + 动态探针、CI 门禁 + 评审。
> ⚠️ 前提是**先说清楚每层管哪一段**；否则两层会各写各的，最后谁也说不清
> 哪一类问题归谁。

### 我自己的注释把粗网判红了——注释里的字面量不是调用点（第三十一批）

那个失败项 `["chat-reasoning"]` 的来源**不是**代码，是**我上一批刚写的注释**：

```ts
// 此前这里还挂过一个 `listen('chat-reasoning', …)`，而后端**从来不发这个事件**
```

粗网按**文本**抽取前端调用 ⇒ 注释里的 `listen('…')` 被当成了真订阅。
⇒ 这是「手写词法分析器把注释里的东西当真引用」的**又一次**，
与第二十七批（i18n 键藏在三元表达式里）、第三十批（正则吞掉嵌套泛型）同族。

修法分两步：

1. **注释改写**：不照抄监听调用的写法；
2. **粗网加固**：前端那一侧先过 `strip_comments()`（屏蔽注释，**保持长度不变**），
   并给屏蔽器**自己加一条自测**（行注释 / 块注释里的调用被去掉、
   字符串里的 `//` 必须留下、真调用必须留下、长度不变）。

⚠️ **后端那一侧刻意不剥注释**：Rust 的 `'` 是**生命周期**而不是字符串，
套 JS 那套屏蔽器会把代码整段吃掉（假阴性）。后端那一侧保持原语义
（「在 Rust 源码里出现过」），这正是粗网的粗。

> **判据五**：**屏蔽注释的解析器必须跟踪字符串。**
> 朴素的「按 `//` 切到行尾」会把 `https://…` 之后的内容整段吃掉——
> 而源码里**到处都是 URL**。这类「看起来对但会吃掉真引用」的解析器，
> 表现是**静默少抽**，和「真的没有」在报告里无法区分。
> ⇒ 屏蔽器要**保持长度不变**（位置与行号才对得上），并配一条
> 「字符串里的 `//` 必须留下」的自测。
> **泛化**：任何手写词法分析器——注释剥离、字符串提取、导入解析、宏展开。
